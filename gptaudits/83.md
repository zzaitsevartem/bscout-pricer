# Общий поиск после подтверждения кандидата — 2026-11-15

Уточнение владельца: исходный сценарий общий для предложений разных моделей и деталей; искали полное название поставщика. Предыдущая приёмка только по конкретной модели не проверяла этот сценарий и была недостаточной.

## Причина и воспроизведение

Frontend вызывает `/api/products/catalog` через `frontend/src/models/catalog/service.ts`. До исправления каталог сопоставлял поисковый запрос с `Product.canonical_name`, но не с названием связанного предложения. На отдельном PostgreSQL и Redis два нейтральных случая (разные модели, детали, коды и цвета) воспроизвели ошибку: approve вернул 200, связь и решение сохранились, очередь опустела, а поиск каталога по полному названию поставщика вернул пустой результат. Оба параметра теста были красными до изменения production-кода.

## Проверки

- После изменения **3 focused integration cases passed, 0 skipped**: два настоящих Device/PartType/Cluster, подтверждение кандидата, сохранение связи, поиск по полному названию поставщика и canonical name, соответствующие facets; третий тест проверяет границы магазина, цены, наличия, неактивного и непривязанного offer и принадлежность конкретному товару. Финальный повтор использовал фактический `normalize_name` парсера: исходное название содержит скобки, а сохранённое нормализованное отличается. Лог `/private/tmp/bscout-general-search-focused.log`.
- Полный релевантный прогон `test_moderation_api.py`, `test_comparison_api.py`, `test_search_vocabulary.py`: **80 passed, 5 failed**. Пять существующих проверок анонимного доступа ожидают 403, актуальные зависимости возвращают 401. Ошибки авторизации не менялись в рамках этой задачи. Лог `/private/tmp/bscout-general-search-tests.log`. Прогон предшествовал финальному усилению фикстуры нормализацией, которое отдельно проверено focused тестом выше.
- Проверки выполнялись на временных изолированных PostgreSQL и Redis; пропуски считаются ошибкой runner. Реальные `.env` не читались.

## Ограничения

Изолированные тесты подтверждают поведение текущего кода, но не доказывают применение к работающему backend и проверку в браузере. Результаты runtime-проверки добавляются отдельно.

## Проверка работающего localhost backend

- Пересобран и пересоздан только Compose service `backend` (`docker compose build backend`; `docker compose up -d --no-deps backend`). БД, Redis и workers не пересоздавались. Контейнер healthy, image `sha256:d89ab9f9c9a0c482d170f79fc1cd214ca0304426fb6427e5e93162f2cbad9cdb`.
- Authenticated live `GET /api/products/catalog?q=Тачскрин для Sony Xperia C C2304 (черный)` вернул 200, total=1, product 9459, source offer 100904. Live `/api/products/catalog/facets` с тем же q вернул 200, total=1, device Xperia C и part type Тачскрин.

User query с оригинальными скобками сработал по `normalized_title`: parser lowercases and replaces punctuation/whitespace, сохраняя слова, including `для` and model codes.
- Это проверка API на локальном Compose backend, не browser rendering и не удалённого production deployment.

## Ручное решение и browser acceptance

Второй обнаруженный дефект: добавленная ранее повторная проверка extractor в approve могла возвращать 409, не позволяя администратору принять решение. Нейтральная интеграционная регрессия воспроизвела 409 до удаления guard; после удаления три focused теста approve и поиска прошли без пропусков. Оригинальное название предложения теперь отображается рядом с магазином в detail; тест таблицы до этой правки падал. Компонентные проверки на отдельной копии frontend с lock-совместимым Vitest 4: **74 passed** (14 файлов, включая тесты ошибок модерации 409/429 и таблицы предложений). Текущий установленный в исходном frontend Vitest 2 не поддерживает конфигурацию projects и без jsdom дал `document is not defined`; тестовый прогон выполнялся с зависимостями отдельной копии, реальные `.env` не читались.

В Chrome проверена полная цепочка с нейтральной фикстурой на отдельных настоящих Next, FastAPI, PostgreSQL и Redis. Только первый запрос approve был подменён тестовым 409: ошибка появилась рядом с модерацией, кандидат остался в очереди. После снятия подмены второй клик выполнил настоящий POST, кандидат исчез из pending; поиск по полному названию открыл detail, где исходное название и ссылка того же offer видны в одной строке. Дополнительно API подтвердил id, title и URL. В реальной базе эта проверка не создаёт и не изменяет фикстуры; внешний сайт не открывался.
