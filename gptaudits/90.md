# Ошибочные типы предложений и административное удаление — 2026-11-16

Ветка: `bscout/бскаут-тест`. Коммитов нет. Не связанное изменение `frontend/src/widgets/authorizedHome/ui/TrackingPreviewCard.tsx` сохранено. Оркестрация по запросу пользователя: Luna — чтение проекта/всей локальной БД, Sol — код и runtime, Terra — регрессионные тесты.

## Причина и охват

Luna проверила снимок всей доступной локальной БД: 18 271 предложений, 4 703 с привязкой, четыре магазина. Это не проверка production. Классификатор выбирал совпавший тип детали из названия без различения продаваемого предмета и детали, для которой он предназначен. Поэтому «Скотч фиксации дисплея» стал дисплеем, а «Стекло камеры» — камерой. Отдельного типа для проклеек/уплотнителей в текущем словаре нет. Автоматическое создание одной общей карточки проклейки склеило бы проклейки аккумулятора, крышки и дисплея одной модели.

Подтверждены семьи ошибок: стекло камеры (144 в исходном снимке); скотч/проклейки дисплея, аккумулятора и крышки (61 по исходной проверке Luna). 157 названий шлейфов для кнопок/зарядки неоднозначны, массовое изменение не выполнялось. Настоящие дисплейные модули с `(Переклей)` и комплекты стекла с OCA сохранены. Числа относятся к снимкам: параллельно продолжались ранее запущенные обходы, поэтому состав БД менялся.

Extractor теперь не присваивает тип целевой детали расходнику, стоящему перед ним в названии; стекло камеры не объединяется ни с камерой, ни с экранным стеклом. Такие предложения остаются для проверки (`review` или `unmatched`, в зависимости от распознанной модели). Это предотвращает известные ложные объединения; полнота семантического распознавания всех возможных названий не заявляется.

## Удаление по ПКМ

В таблице предложений карточки администратора ПКМ открывает «Удалить», также работает клавиша контекстного меню / Shift+F10. Кастомный dialog подтверждает действие, показывает pending/ошибку, не использует `window.confirm`. Для обычного пользователя меню отсутствует. `DELETE /api/admin/offers/{id}` защищён `get_current_admin`; выбранное предложение отвязывается, получает `rejected` и становится неактивным. История сохраняется. Повторный парсинг не активирует отклонённое предложение, matching защищает `rejected`, агрегаты и клиентские запросы обновляются.

Администратор без подписки получил адресный доступ к GET карточки `/products/catalog/{id}`. Остальные платные API сохранили проверку подписки. Порядок статических маршрутов catalog/devices/facets перед динамическими сохранён.

## Исправление данных и возврат

`scripts/ops/quarantine_contextual_offers.py` по умолчанию показывает кандидатов. `--apply` сохраняет JSON до исправления, изменяет только актуальные auto-привязки проверенных семей на review/null, закрывает устаревшие pending/approved кандидаты и пересчитывает агрегаты под общим advisory lock. Пользователи, цены и исходные предложения не удаляются. `--restore <snapshot.json>` возвращает привязки только для всё ещё review/null строк с неизменённым названием, не затирая последующую модерацию.

Первый dry-run: 202. При apply из-за активных обходов уже 210, все auto. Снимок `.unlazy/contextual-offers/20261115T212055Z.json`: 210 уникальных предложений, структура проверена; SHA256 `7704568972e565a4006d5035027456de830d6542b8f45ecd36a4b054cc8af8d2`. ## Завершение runtime

Мягкая остановка worker завершилась штатно: текущие задачи дошли до checkpoint и вернули `continued` (TGSM602с), затем контейнер остановился. Принудительное завершение не понадобилось. Worker пересоздан из нового образа, продолжения прежних обходов снова выполняются. SHA256 extractor и parser_service внутри работающего worker совпали с файлами ветки.
