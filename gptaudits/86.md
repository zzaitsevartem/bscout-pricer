# Пересмотр кандидатов и устранение причины — 2026-11-15

Продолжение 85: пользователь прямо потребовал разобрать всех кандидатов, проверить десять товаров через поиск и устранить причину, а не только последствия. Предыдущие ответы о завершении были ошибочными.

## Причина и защита

Причина существовавших 113 предложений: старый extractor допускал fuzzy edit-distance совпадение короткого префикса названия устройства с alias более длинной модели. Общая защита в extractor отклоняет fuzzy совпадения при strict prefix в обе стороны; точное совпадение и исправление других опечаток сохраняются. Нейтральные синтетические unit регрессии добавлены ранее; условий, специфичных к конкретной модели, нет.

Дополнительная причина сохранения неверных рекомендаций: при повторном матчинге старые pending строки не закрывались, если текущий extractor больше не предлагал тот же товар. Теперь при повторном матчинге старые pending кандидаты, не совпадающие с текущим результатом, получают `superseded`. Это технический статус, не человеческий reject: decided_by и decided_at не задаются. Если тот же алгоритм позже снова предложит этот продукт и у кандидата не было человеческого решения, superseded возвращается в pending. Approved и rejected никогда не переоткрываются. Статус добавлен миграцией, API и фильтром «Устарели»; история строки сохраняется. Миграция upgrade проверена на чистой изолированной PostgreSQL и применена к локальной рабочей БД.

## Вручную рассмотренные предложения

Снимок текущих 113 pending кандидатов с названиями, предполагаемыми карточками и URL отдельно проверен вручную по названиям. Они предлагали одну модель, тогда как названия указывают другие модели/совместимости. В одной транзакции под catalog advisory lock все 113 были перепроверены по ID, статусу, предыдущему продукту, названию, URL, активности и отсутствию ручного решения. Строки переведены в superseded; имена, старые связи кандидатов, features и человеческая история сохранены. Автоматическое человеческое подтверждение или отклонение не подделывалось.

Для каждого из 113 предложений создана отдельная карточка `review-offer|<offer_id>` с исходным названием поставщика. Она содержит строго одно исходное предложение и URL, не приписывает устройству другое имя и сохраняет offer в `review`. Это временное поисковое представление до классификации модели и совместимости, НЕ утверждение, что конкретная совместимость независимо проверена по сайту магазина. Парсер сохраняет такую карточку при повторном проходе и обновляет название при изменении исходного предложения. После ручной отвязки карточка без активного предложения не выдаётся в каталоге. Обычные карточки без предложений сохраняют прежнее поведение.

Запись guarded repair проверена на 113 фикстурах отдельной PostgreSQL перед применением. Первый isolated run выявил несдвинутый sequence в тестовых данных с ручными ID; исправлен только sequence тестовой базы, повтор дал 113. Снимки до/после и код: `.unlazy/matching-audit-2026-11-15/pending-reviewed.json`, `candidate-repair.log`, `candidate-repair-snapshots.json`, `repair_candidates.py`. `rollback_candidates.py` не пишет без `--apply` и проверяет текущие значения всех 113 строк; dry-run прошёл. При реальном rollback служебные карточки становятся пустыми и скрываются из каталога, история предложений остаётся.

## Проверка

На отдельной PostgreSQL/Redis прошли 7 целевых интеграционных случаев без пропусков: ручной override, поиск после approve для двух нейтральных моделей, фильтры offer, перевод устаревшего кандидата без фиктивного админа, поиск review-карточки и её исчезновение после отвязки, сохранение обычных пустых карточек. Фронтенд TypeScript и lint, Python Ruff и git diff --check прошли. Тесты до исправления flush обнаружили, что статус не сохранялся при полностью нераспознанном предложении; добавлен flush, повтор прошёл.

После исправления рабочей базы проверены 10 полных названий из Либерти (4), Профи (3), ТГСМ (3): для каждого authenticated `/api/products/catalog` нашёл именно его карточку с исходным названием и источником, `/api/products/catalog/{id}` вернул тот же offer ID и URL. Через Chrome дополнительно проверена цепочка поиск → карточка → detail с исходным названием и ссылкой магазина. Все 113 строк проверены read-only: superseded, без decided_by/at, offer review, карточка имеет соответствующие название и ID.

До этого тот же поиск первых десяти pending вернул 0 результатов. Данное исправление покрывает их выдачу без ложной классификации; ручное присвоение совместимости моделям и объединение разных поставщиков остаётся отдельной задачей, которую нельзя достоверно решить по одному названию.
