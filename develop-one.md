## Этап 1 — выполнять сейчас

1. **Rate limit во всём проекте.** Инвентаризировать публичные и авторизованные
   маршруты, вход/регистрацию/восстановление, поиск, экспорт, импорт, административные
   и ресурсоёмкие операции. Настроить соразмерные ограничения и идентификацию
   клиента/пользователя, корректную работу через доверенный proxy и несколько
   процессов. Учесть специальные требования webhook и фоновых процессов.
   Проверить нормальные запросы, превышение лимита, восстановление доступа,
   изоляцию пользователей и поведение при недоступном Redis. Не блокировать
   штатную работу приложения; политику отказа выбрать и обосновать по маршрутам.
2. **Секреты в ошибках.** Убрать пароль и другие чувствительные значения из
   validation responses, включая подтверждённый ответ 422 регистрации.
   Проверить связанные auth-сценарии и логи; сохранить полезные ошибки формы.
3. **Уязвимые зависимости.** Проверить актуальные advisories backend/frontend,
   обновить зависимости и согласовать используемые manifests/lock-файлы.
   Проверить совместимость. Последний npm audit показал 30 уязвимостей:
   12 moderate, 14 high, 4 critical, включая Next.js; это снимок, а не фиксированная
   цель для следующего запуска. Неразрешённые находки явно обосновать.
4. **Один реальный источник полностью.** Выбрать один согласованный источник и
   проверить импорт → сохранение предложений → каталог → поиск → карточку →
   корректную ссылку магазина. Сохранить происхождение данных. Fixtures и моки
   использовать для регрессии, но не выдавать их за живой прогон. Для выбора
   источника использовать существующие настройки/решения; при отсутствии
   согласованного источника запросить его выбор, продолжая независимые задачи.
5. **Выбранный тариф после регистрации.** Сохранить выбор из `/register?plan=...`
   и после успешной регистрации вернуть пользователя к оформлению выбранного
   плана. Валидировать значение; выбор тарифа не должен сам выдавать платный доступ.

## Что уже проверено и не требует повторной реализации

Импорт приложения и configure_mappers проходят на SQLAlchemy 2.0.35 и 2.0.51;
passlib 1.7.4 / bcrypt 4.0.1 хешируют короткий пароль; формы вызывают auth API;
logout отзывает refresh; production guard отклоняет известный JWT-secret;
при запуске зарегистрированы четыре парсера. Это доказательства для проверенной
ветки/среды, а не гарантия другой развёрнутой сборки. Не объявлять это «недавно
исправленным»: время исходного аудита не объясняет расхождения.

- Основной оркестратор — настроенный Sol; небольшие ясные изменения делать
  напрямую. Следовать `.agents/skills/bscout-orchestrate/SKILL.md`.

- Отдельного кодера Sol подключать только для полезной независимой части,
  указав точное владение файлами, зависимости и запрет откатывать чужие изменения.
  Не запускать обязательную цепочку reader → coder → reviewer для каждой задачи.
- Terra/Astra не использовать по умолчанию; смена модели/стоимости требует
  решения владельца. Reviewer нужен для рискованных auth/security изменений,
  а не для каждого небольшого исправления.
- Использовать `/Users/zzaitsevartem/.codex/skills/unlazy/SKILL.md`. Если путь
  недоступен, найти установленный skill; не подменять его заявлением об успехе.
- До реализации зафиксировать acceptance gates на все пять задач этапа 1 в
  локальном `.unlazy/develop-one/`. При реальной делегации использовать контракт,
  дерево, отдельные leaf/node gates, ownership leases и launch waves по skill.
  Не создавать второй живой task plan; PLAN внутри unlazy служит только
  контрактом проверки/диспетчеризации и ссылается на MASTERPLAN.

- Полученные результаты проверять независимо, исполняемые gates повторять
