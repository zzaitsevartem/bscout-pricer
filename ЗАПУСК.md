# Запуск BScout на новом компьютере

Инструкция для локальной разработки на macOS или Linux. Все команды выполняйте из корня репозитория, если не указано иное.

## 1. Установить инструменты

Установите Git, Docker Desktop (запустите Docker), Node.js с npm и Python 3.11. Проверка:

```bash
git --version
docker --version
docker compose version
node --version
npm --version
python3.11 --version
```

## 2. Получить проект

Попросите владельца репозитория добавить ваш GitHub-аккаунт в collaborators. Настройте доступ GitHub через SSH или GitHub CLI, затем:

```bash
git clone https://github.com/zzaitsevartem/bscout-pricer.git
cd bscout-pricer
git status --short
```

Для начала работы на конкретной ветке:

```bash
git fetch origin
git switch --track origin/<имя-ветки>
```

Например, последние изменения поиска и отслеживания устройств находятся в `bscout/tracking-search-delete-2026-11-13`.

## 3. Создать локальные `.env` файлы

В репозитории есть **три шаблона `.env.example`**. Шаблоны — обычные файлы, они хранятся в Git и доступны разработчику после клонирования. Команда `cp` создаёт рядом локальную копию с именем, которое приложение ожидает. Редактировать нужно копии `.env`, сами `.env.example` оставьте без изменений.

Запустите из корня репозитория:

```bash
cp .env.example .env
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env.local
```

Проверьте наличие созданных файлов, не выводя их содержимое:

```bash
ls -l .env backend/.env frontend/.env.local
```

Что за что отвечает:

| Локальный файл | Используется для | Нужно менять для обычного локального запуска? |
| --- | --- | --- |
| `.env` | Docker Compose: порты, `JWT_SECRET_KEY`, флаги запуска | Порты можно оставить. Поменяйте `JWT_SECRET_KEY` на свой случайный ключ и такое же значение задайте в `backend/.env`. |
| `backend/.env` | Конфигурация backend и worker: адреса PostgreSQL/Redis, JWT, почта и интеграции | Для локальной БД значения шаблона совпадают с `docker-compose.yml`; почта, VK, YooKassa и Telegram можно оставить пустыми, если задача их не требует. |
| `frontend/.env.local` | Настройки Next.js: адрес backend и локальный адрес сайта | Оставьте `http://localhost:8000` и `http://localhost:3000`. |

Для локальной разработки PostgreSQL и Redis запускаются в Docker. Compose задаёт им локальные учётные данные `bscout`/`bscout`, а backend-контейнер получает адреса сервисов внутри Docker-сети. Не меняйте эти значения по отдельности: при изменении обновите конфигурацию согласованно.

В `JWT_SECRET_KEY` в корневом `.env` и `backend/.env` должен быть один и тот же случайный локальный ключ. Сгенерируйте его командой:

```bash
openssl rand -hex 32
```

Скопируйте результат в оба файла в строку `JWT_SECRET_KEY=...`. Это локальный ключ разработчика, он не должен совпадать с production-ключом. Если OpenSSL не установлен, можно пока оставить шаблонное значение только для изолированной локальной разработки; никогда не используйте его на публичном сервере.

**`.env` файлы никому отправлять не нужно**, в том числе через мессенджер. Новый разработчик создаёт их сам по этим шагам. Они игнорируются Git. Перед коммитом проверьте:

```bash
git check-ignore -v .env backend/.env frontend/.env.local
git status --short
```

Команда `git check-ignore` должна показать, что все три файла исключены из Git. Если задаче требуются внешние интеграции, владелец выдаёт отдельные тестовые доступы через одобренное хранилище секретов, а не пересылает production `.env`.

### Нужно ли вручную создавать TOML и другие конфиги?

Обычно нет. В отличие от `.env`, проектные конфиги уже закоммичены в репозиторий: например, `backend/pyproject.toml`, `backend/alembic.ini`, `frontend/package.json`, `frontend/tsconfig.json`, `frontend/next.config.mjs`, `docker-compose.yml` и файлы CI. Git скачает их при `git clone`; создавать или пересылать эти файлы вручную не нужно. Lock-файл `frontend/package-lock.json` тоже уже в репозитории; для установки используйте npm и `npm ci`.

Итого для стандартного запуска разработчик **вручную создаёт только три локальных env-файла** командами `cp` выше. TOML, YAML, JSON и остальные конфиги он получает из Git. Создавать дополнительный конфиг нужно только если конкретная задача или локальная интеграция этого требует; тогда сначала проверьте, есть ли для него шаблон в репозитории.

## 4. Запустить backend и базовые сервисы

Из корня проекта:

```bash
docker compose up -d postgres redis backend
docker compose ps
```

Дождитесь состояния `healthy` у PostgreSQL и backend, если healthcheck отображается. Примените миграции из контейнера backend:

```bash
docker compose exec backend python -m alembic upgrade head
```

API будет доступен по адресу `http://localhost:8000`; документация — `http://localhost:8000/docs`.

> Не запускайте production Compose и не подключайте локальную разработку к рабочей базе.

## 5. Запустить frontend

В отдельном окне терминала из корня репозитория:

```bash
cd frontend
npm ci
npm run dev
```

Откройте `http://localhost:3000`. Frontend использует `BACKEND_URL=http://localhost:8000` из `frontend/.env.local`.

## 6. Дополнительные фоновые задачи

Для большинства задач поиска и интерфейса достаточно PostgreSQL, Redis и backend из шага 4. Если разрабатываете парсеры, очереди или периодические задания, дополнительно запустите:

```bash
docker compose up -d worker mail-worker beat
```

## 7. Проверить изменения перед отправкой

Backend-тесты запускайте в Docker-контейнере backend или в отдельном Python 3.11 окружении, настроенном на тестовые PostgreSQL и Redis. Интеграционные тесты очищают тестовую базу и Redis; не запускайте их, пока не проверили, что `TEST_DATABASE_URL` указывает именно на отдельную тестовую базу.

В контейнере backend:

```bash
docker compose exec backend python -m pytest tests/unit
docker compose exec backend ruff check src tests
```

Frontend:

```bash
cd frontend
npm test
npm run lint
npm run build
```

## 8. Рабочий цикл Git

Создайте ветку для своей задачи, проверьте изменения и отправьте её в GitHub:

```bash
git switch -c feature/<короткое-имя-задачи>
git status --short
git diff --check
git add <изменённые-файлы>
git commit -m "Краткое описание изменения"
git push -u origin feature/<короткое-имя-задачи>
```

Затем откройте Pull Request в GitHub. Не добавляйте в коммит `.env`, `node_modules`, виртуальные окружения, локальные данные базы и build-файлы.

## Остановка

Остановить сервисы, сохранив локальные данные:

```bash
docker compose stop
```

Не используйте `docker compose down -v`, если хотите сохранить локальную базу PostgreSQL.
